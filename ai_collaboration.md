# Human-in-the-Loop AI Collaboration

This project was developed as a software-defined UGV/GCS cybersecurity testbed, but its implementation process was also a controlled experiment in human-in-the-loop AI-assisted engineering. The core concept, architecture, and security direction were led by the developer. The developer defined the testbed as a defense UGV-inspired software abstraction rather than a replica of a real military vehicle, and shaped the project around a two-layer architecture: a Simulation Layer for QGroundControl, Gazebo, RViz, ROSbot motion, odometry, and scan feedback, and a Software-Defined UGV Security Layer for command mediation, mission validation, GNSS input validation, correlation, and hold/block response.

The security components were also developer-directed. The MAVLink Bridge was designed as the translation and mediation point between GCS-side MAVLink traffic and ROS2-side robot control. Mission Audit was framed as a pre-execution validator for uploaded missions, checking geofence boundaries, waypoint jumps, altitude ranges, command allowlists, and mission sequence integrity before acknowledging or rejecting a mission. GNSS Integrity was designed to treat MAVLink `GPS_INPUT` as a software-defined position-input attack surface, comparing incoming coordinates and quality fields against the simulated UGV state. The Correlation Engine was introduced to avoid isolated, one-off decisions: mission rejection, GNSS rejection, and high-risk commands are combined into a risk score that can trigger hold, zero command output, and command blocking.

Claude and Codex were used as supporting agents inside this developer-led workflow. Claude acted primarily as an orchestrator and reviewer. Its role was to break work into batches, inspect the direction of each change, identify likely bugs or mismatches, and hold the implementation to a consistent quality bar. Codex acted as the implementation agent, applying concrete code and documentation changes, running local checks, and reporting diffs back for review. The developer remained in the loop throughout the process, relaying Claude's review instructions to Codex, deciding when a proposed change was acceptable, and correcting direction whenever the work risked drifting away from the intended testbed goal.

This workflow improved the project in several concrete stages. The first batch addressed a GNSS startup false-positive risk. Before the simulated UGV had produced odometry, GNSS validation could treat the lack of reference state as a rejection condition. That behavior was refined so startup GPS input without odometry is classified as `no_reference`, still logged for observability, but not escalated into a correlation signal. The second batch aligned the standard runtime profile around `rosbot_xl` with the `autonomy` configuration, and synchronized `.env.example`, `README.md`, and `compose.webui.yml` so the documented profile matched the actual target testbed. The third batch paused implementation and checked the live Docker and ROS2 state, confirming that the simulation and RViz containers were running, that ROS2 topics such as `/cmd_vel`, `/odometry/filtered`, `/scan`, `/scan_filtered`, and `/tf` existed, and that QGroundControl and the Bridge still needed to be brought into the live end-to-end run.

The later batches strengthened the testbed's ability to produce repeatable evidence. The fourth batch added recovery visibility to the Correlation Engine: after a hold period expires and a new command is evaluated, the engine can now log a `hold_released` event and send an informational MAVLink status text. The fifth batch introduced a host-side evidence runner that calls the Bridge container's MAVLink test tools in sequence for the Day3 through Day6 scenarios. The sixth batch expanded that runner into a more report-friendly evidence structure under `docs/evidence`, added the `malicious_jump` mission case, and captured snapshots of mission audit, GNSS integrity, correlation, Docker state, and Bridge environment information.

The important point is that the AI agents did not originate the project concept or replace engineering judgment. They accelerated implementation, helped catch consistency problems, and provided structured review pressure. The developer supplied the project intent, threat model, architectural boundaries, and final decisions. Claude and Codex operated inside those boundaries as review and implementation aids. This made the workflow faster without removing accountability: every claim still had to be tied back to source code, runtime behavior, logs, or explicit limitations.

The resulting collaboration pipeline can be summarized as developer-led design with AI-assisted review and execution. The developer defines the objective and accepts or rejects direction. Claude reviews plans and implementation quality. Codex performs bounded changes and local verification. The loop repeats until the implementation, documentation, and evidence match the intended software-defined UGV/GCS cybersecurity testbed.
